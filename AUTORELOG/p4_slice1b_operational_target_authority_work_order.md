# P4 Slice 1B Design Freeze: Operational Target Authority Binding

Status: design freeze and work-order for review. Implementation is **NO-GO**
until this document is explicitly approved.

Date: 2026-09-13  
Baseline: `main` after PR #31 squash merge at
`34c77fab0e469c2219370c61f81a61e0e7215b03`  
Foundation evidence: **13/13 PASS**; local verification `182 passed, 86
subtests`  
Issue #1 checkpoint: `5654284129`  
Runtime owner: `LEGACY`

This document freezes the narrow operational-target contract that follows the
Local Agent Binding Authority / Lease Foundation. It does not create an
implementation branch, alter runtime code, authorize dispatch, or change the
current ownership model.

## 1. Objective

Prepare future operational jobs and targets so that no later claim or dispatch
can rely on an incomplete, inferred or stale authority context.

The exact authority context is:

```text
host_id
+ profile_id
+ binding_generation
+ verified_identity_ref
+ verified_identity_revision
+ authority_epoch
+ fence_counter
+ idempotency_key
```

The fence identity is the exact pair:

```text
fence_identity = (authority_epoch, fence_counter)
```

Every future operational target must carry the full context. A target that
cannot carry it is not executable authority. A positive Slice 1B result means
only `AUTHORITY_BOUND_TARGET / RECORDED` or
`AUTHORITY_BOUND_TARGET / CLAIMED`; it does not mean dispatch permission,
runtime ownership or an `ACTIVE` transition.

## 2. Frozen boundaries

- `host_id`, `profile_id` and `binding_generation` are the exact binding
  identity. Matching only host and profile is invalid.
- `verified_identity_ref` is the non-secret identity reference from the
  authoritative Portable Domain Store snapshot. It is never inferred from
  `account_ref`, display name, session state or remote observation.
- `verified_identity_revision` is the independent monotonic verification-event
  revision. A matching reference with a stale revision is still invalid.
- `authority_epoch` and `fence_counter` are operational fence evidence. They
  are generated by the canonical authority coordinator, not supplied by a
  caller or restored as live authority from backup data.
- `idempotency_key` identifies one intended job operation. Reuse resolves only
  to the same recorded context and record identity; a conflicting context
  fails closed.
- P3 generations and the Portable Domain Store remain separate from mutable
  operational job/target state. No `ATTACH`, cross-database transaction claim,
  or write to a P3 generation is permitted.
- The current P4 `jobs` and `leases` foundation remains historical/job
  infrastructure. It is not silently promoted to runtime authority by the
  presence of a row, owner, timestamp or lease name.
- Runtime owner remains `LEGACY` for the entire slice.

## 3. Scope

### Included in the design

1. An authority-bound target contract containing the eight required context
   values above.
2. Durable job provenance and idempotency semantics for recording a target.
3. Fail-closed revalidation contracts at enqueue, claim and future-dispatch
   boundaries.
4. Explicit stale, mismatch, legacy and restore quarantine semantics.
5. Acceptance evidence proving that the slice records and validates targets but
   performs no remote or runtime side effect.

### Not included in the implementation authorization

This design does not authorize any code change. In particular, it does not
authorize:

- remote commands, WebSocket reads or remote mutations;
- scheduler handoff, AutoCycle ownership or worker dispatch;
- runtime takeover, Login/Reconnect or `ACTIVE` transitions;
- Flask/API/UI control wiring or changes to `db.html`;
- Quick Tunnel, Task Scheduler, process spawn/kill or mutex ownership changes;
- automatic migration of old jobs into executable authority;
- backup/restore revival of actionable jobs or leases;
- a new implementation branch before formal design approval.

## 4. Authority-bound target contract

The future target record must make the complete context explicit and inspectable
before it can become claimable:

| Field | Contract |
|---|---|
| `target_id` | Stable target record identity; never inferred from a viewed profile. |
| `job_id` | Durable job identity linked to exactly one target context. |
| `host_id` | Required non-empty host identifier. |
| `profile_id` | Required non-empty profile identifier. |
| `binding_generation` | Positive generation from the exact binding snapshot. |
| `verified_identity_ref` | Required non-secret verified identity reference. |
| `verified_identity_revision` | Positive independent verification-event revision. |
| `authority_epoch` | Current coordinator epoch; opaque and non-empty. |
| `fence_counter` | Positive monotonic counter within that epoch. |
| `idempotency_key` | Required stable key for the intended operation. |

The target may additionally carry operation kind, requested-by/request ID,
creation time, source snapshot reference or digest, and a schema/contract
version. Those fields provide provenance; they do not replace any required
authority field.

No password, cookie, bearer token, session material, remote payload, PID or
secret path is part of this context or its audit evidence.

## 5. Job lifecycle for Slice 1B

Slice 1B records and validates intent only:

```text
requested -> recorded -> claimable -> claimed
                         |            |
                         +-> quarantine +-> quarantine
```

- `requested` is caller input and has no authority.
- `recorded` means the exact context and provenance were persisted; it does
  not enqueue a remote action or open a connection.
- `claimable` means the target passed record-time checks and may be considered
  by a future claim operation.
- `claimed` means a worker/owner transaction recorded a claim after claim-time
  revalidation. It still does not authorize dispatch in Slice 1B.
- `quarantine` is terminal for that attempted context until an explicit,
  separately defined reconciliation creates a new idempotency key and fresh
  evidence. Quarantine never silently repairs the old row.

The existing P4 dispatch lifecycle (`dispatched`, `succeeded`, `failed`,
`unknown`) is outside this slice. Slice 1B must not create a path into those
states or claim that a recorded/claimed row was remotely applied.

## 6. Provenance and idempotency

Every recorded target must preserve:

- the complete authority context exactly as validated;
- the operation kind and target identity;
- the request/actor provenance available at record time;
- the authoritative snapshot reference or digest used for validation;
- creation time from the canonical store/coordinator boundary;
- the idempotency key and its context fingerprint;
- a sanitized rejection/quarantine reason when recording is refused.

Before any new row is created, the authority-bound target path must look up the
idempotency key. If it already exists, the response must return the exact same
`job_id`, `target_id`, context fingerprint and current terminal status. A
quarantined row is terminal for that key: same-key replay must not create a
second row, reactivate it, move it back to `claimable`, or reclaim it. The
lookup must fail closed when the key resolves to a different host, profile,
generation, identity, revision, fence pair or operation target. A corrective
operation uses a new key and records its relationship to the old
quarantined/unknown record; it does not overwrite evidence.

## 7. Required revalidation boundaries

Portable and Operational SQLite remain separate. Each boundary reads and
compares both stores; it does not claim a cross-database atomic commit. The
initial snapshot is optimistic evidence only. The Operational transaction must
revalidate Portable state and the current fenced lease immediately before its
commit.

### 7.1 Enqueue/record boundary

The future enqueue adapter must:

1. Read one authoritative Portable snapshot for the exact binding triple.
2. Reject missing, conflicting, `OFFLINE`, `RETIRED`, revoked or otherwise
   non-authoritative binding state.
3. Verify the snapshot's identity reference and independent revision.
4. Begin `BEGIN IMMEDIATE` on the canonical Operational store.
5. Obtain the current operational lease/fence evidence and write a provisional
   target that is not claimable.
6. Re-read the authoritative Portable snapshot and current fenced lease while
   still in the Operational transaction, immediately before commit.
7. If every authority field and provenance fingerprint still matches, promote
   the provisional row to `recorded`/`claimable` and commit. If Portable or
   Operational revalidation drifts or is unavailable, roll back the
   provisional write; when the Operational store is available, persist a
   separate terminal quarantine record for the same key rather than an
   executable target.
8. Return a recorded/claimable result only; do not call a scheduler, worker,
   WebSocket or remote script.

Any mismatch rejects before an executable target is recorded. No missing field
may be filled from a currently viewed profile, an older lease, a legacy job or
an account reference.

### 7.2 Claim boundary

Claim must read an initial Portable snapshot, enter `BEGIN IMMEDIATE` on the
canonical Operational store, write only a provisional claim, then re-read the
Portable snapshot and current fenced lease immediately before commit. It must
compare:

```text
host_id
profile_id
binding_generation
verified_identity_ref
verified_identity_revision
authority_epoch
fence_counter
idempotency_key
```

It must also verify owner, lease state, expiry, binding state and target/job
provenance. A stale revision, stale fence, binding drift, profile mismatch,
competing live lease or idempotency conflict rolls back the provisional claim
and records quarantine when possible. Claiming only marks operational state; it
does not dispatch.

### 7.3 Future-dispatch boundary

The design reserves a final check immediately before any future dispatch. The
check must repeat the same complete comparison and reject any stale or mixed
context. Slice 1B has no dispatch implementation: its acceptance adapter must
return a deterministic no-dispatch result and record evidence that the remote
dispatch count remains zero.

No future slice may remove this boundary because enqueue and claim previously
passed.

## 8. Fail-closed mismatch matrix

| Condition | Required result | Forbidden behavior |
|---|---|---|
| Any required authority field is missing or malformed | Reject/quarantine | Fill defaults or infer from current UI/profile |
| Profile or host is unknown | Reject | Create identity during validation |
| Binding triple is absent, duplicated or superseded | Reject | Match by host/profile only |
| Binding is `OFFLINE`, `RETIRED`, revoked or non-authoritative | Reject | Convert to `ACTIVE` or proceed read-as-authority |
| Identity reference differs from the snapshot | Reject/quarantine | Fall back to account/display name |
| Identity revision is stale or missing | Reject/quarantine | Treat equal identity text as fresh proof |
| Fence epoch differs | Reject/quarantine | Accept restored or old epoch |
| Fence counter is stale, reused or non-monotonic | Reject/quarantine | Accept the older holder |
| Lease is missing, released, expired or owned by another actor | Reject/quarantine | Renew, take over or dispatch implicitly |
| Binding/profile changes across revalidation | Reject/quarantine | Commit mixed snapshots |
| Idempotency key conflicts with a different context | Reject/quarantine | Overwrite or replay the old row |
| Existing job lacks complete authority context | Legacy quarantine | Infer context and make executable |
| Backup/restore/restart presents old actionable state | Quarantine/read-only | Revive authority from the restored row |
| Coordinator or canonical store unavailable | Reject/read-only | Self-grant from local cache or SQLite copy |

All rejection evidence contains only a reason class, opaque request/correlation
ID, target/job reference and non-secret context fingerprints. It must not log
credentials, sessions, bearer values, cookies or raw remote payloads.

## 9. Legacy jobs and migration boundary

### Legacy claim path is not an authority path

Authority-bound targets must use a dedicated target/job path that the legacy
generic `claim_job()` predicate cannot select. The preferred contract is a
dedicated `authority_bound_targets` table linked to job provenance; if a shared
table is ever used, a mandatory non-null discriminator and an authority-aware
claim predicate must provide the same structural isolation. An authority-bound
target must never be inserted as an ordinary `jobs.status='queued'` row that
the legacy `claim_job()` can claim through generic `leases`.

Acceptance must call the legacy `claim_job()` against an authority-bound target
and prove that it returns no claim and performs no status, owner, lease or
heartbeat mutation. Only the authority-aware target path may perform the
provisional-claim/revalidation protocol in Section 7.2.

Existing operational jobs, leases or checkpoints without the complete authority
context are historical/legacy records. They must be:

- classified with an explicit legacy/quarantine state;
- retained as audit evidence without inferred authority fields;
- excluded from claimable or executable target selection;
- prevented from becoming executable through `NULL` defaults, account joins,
  viewed-profile state or lease-name matching;
- reconciled only by an explicitly created fresh record with fresh evidence and
  a new idempotency key.

Partial context is equivalent to missing context. The implementation must not
silently migrate old P4 `jobs`/`leases` into the new authority contract and must
not describe a legacy row as an authority-bound target.

## 10. Restart, backup and restore

- A normal restart begins with no actionable claim from a prior process. Any
  new claim must pass the current Portable snapshot and current coordinator
  fence checks.
- An operational restore opens in quarantine/read-only mode until integrity,
  schema identity and a fresh non-backup authority epoch are established.
- Restored jobs and leases are historical evidence until they are explicitly
  classified and revalidated. A restored row never revives actionable
  authority by itself.
- A restored or stale fence pair is permanently rejected for the old context.
- Backup/restore acceptance must prove P3 generations remain byte/hash/mtime
  unchanged and no restored row becomes dispatchable.
- Slice 1B does not implement takeover or restore recovery. It only defines
  the quarantine and evidence boundary that a later approved slice must honor.

## 11. Acceptance evidence required before implementation approval/merge

The future implementation branch must provide all evidence below before its
implementation PR can be approved or merged. These are acceptance gates, not
claims made by this design document. Design approval only permits creation of
the implementation branch; it does not waive any gate.

1. Schema/contract fixtures proving every target carries all eight authority
   fields and remains separate from P3 immutable generations.
2. Enqueue tests for exact binding/profile/generation/identity/revision/fence
   matching, same-key replay of a recorded/quarantined row, and idempotency
   conflict rejection.
3. Claim-time revalidation tests for stale identity revision, identity drift,
   binding generation drift, stale fence, competing lease and profile mismatch.
4. Legacy-job tests proving incomplete old rows are quarantined and never
   become claimable through inference or default migration; a direct call to
   legacy `claim_job()` against an authority-bound target must not claim or
   mutate it.
5. Restart and backup/restore tests proving old jobs, leases and fence pairs do
   not revive actionable authority.
6. Concurrent claim tests proving only one exact authority context can claim a
   target and stale holders are rejected.
7. No-side-effect evidence proving target record/claim opens no WebSocket,
   sends no remote command, calls no remote mutation, and performs no
   scheduler handoff.
8. Explicit counters proving `remote dispatch = 0` for the entire slice.
9. Static/diff evidence proving no Flask/UI, `db.html`, AutoCycle, scheduler,
   Login/Reconnect, `ACTIVE`, Quick Tunnel or Task Scheduler path changed.
10. Runtime ownership evidence proving owner remains `LEGACY` before, during
    and after all Slice 1B tests.
11. Sanitized audit evidence proving mismatch and quarantine records expose no
    secret, credential, session or raw remote payload.
12. Regression evidence that the merged P4 foundation and existing read-only
    contracts remain unchanged.

The acceptance report must identify each check as passed, failed or not run;
there is no implicit pass from a schema migration or a successful local claim.

## 12. Work-order sequence

After this design is approved, the implementation work must follow this order:

1. Freeze the authority-bound target schema and legacy/quarantine states.
2. Add job provenance and idempotency recording without dispatch.
3. Add enqueue/claim validators and serialized claim-time revalidation.
4. Add stale/quarantine/restart/restore semantics and evidence.
5. Run the no-side-effect acceptance suite with dispatch count exactly zero.
6. Stop for review. Do not extend the slice into runtime ownership, scheduler
   handoff or remote dispatch.

The implementation branch must start from the merged `main` baseline above and
must contain only the approved Slice 1B scope. Any runtime, UI, scheduler,
remote or ownership change requires a separate design and approval.

## 13. Review gate

Formal approval must explicitly confirm:

- the eight-field authority context is mandatory and exact;
- fence identity is `(authority_epoch, fence_counter)` and stale pairs reject;
- enqueue and claim record/validate only, with no dispatch;
- the future-dispatch boundary remains mandatory even though dispatch is
  outside this slice;
- stale identity revision, stale fence, binding drift and profile mismatch
  fail closed;
- incomplete existing jobs are quarantined, not inferred into authority;
- restart and backup/restore cannot revive actionable authority;
- acceptance proves remote dispatch is exactly zero and no scheduler handoff,
  `ACTIVE` transition, runtime takeover or Flask/UI control occurs;
- runtime owner remains `LEGACY`;
- implementation remains NO-GO until this approval is recorded.
